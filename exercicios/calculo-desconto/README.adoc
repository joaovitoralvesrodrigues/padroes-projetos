= Cálculo de Descontos

Considere que temos um sistema de vendas onde diferentes formas de desconto podem ser implementadas de acordo com as promoções vigentes, como em datas comemorativas. O sistema deve permitir o cálculo do desconto sobre a venda das seguintes maneiras:

- percentual de desconto definido (que pode vir de um banco de dados);
- percentual de desconto progressivo: `valor da compra/25`, não podendo ultrapassar 20% (este são apenas valores arbitrários de exemplo);
- desconto de 15% na data de aniversário do cliente.

O usuário é quem escolhe o tipo de desconto a ser aplicado, não o programa.
O programa deve apenas permitir que seja mudado o algoritmo de cálculo do desconto.

== Responda

1. Qual padrão de projeto pode ser utilizado no desenvolvimento de uma solução? 
O padrão ideal é o Strategy (Estratégia).

Ele é indicado quando você tem diversos algoritmos para realizar uma tarefa (no caso, calcular descontos) e quer que o objeto original (a Venda) permaneça independente de qual algoritmo foi escolhido. Isso permite trocar a estratégia de cálculo em tempo de execução.
2. Como poderíamos implementar estes tipos de desconto sem utilizar Padrões de Projetos? 
Sem o Strategy, o cálculo provavelmente seria feito dentro da classe Venda usando uma estrutura de switch-case ou múltiplos if-else.

Exemplo conceitual:

public double calcularDesconto(int tipoDesconto) {
    if (tipoDesconto == 1) { // Fixo
        return valorTotal * 0.10; 
    } else if (tipoDesconto == 2) { // Progressivo
        double d = valorTotal / 25.0;
        return d > 20 ? valorTotal * 0.20 : d;
    } else if (tipoDesconto == 3) { // Aniversário
        // Lógica de data aqui...
    }
    return 0;
}

3. Quais os problemas que tal implementação traria?

Violação do Princípio do Aberto/Fechado (OCP): Toda vez que uma nova promoção surgir, você terá que abrir a classe Venda e modificar o código existente, correndo o risco de quebrar o que já funciona.

Dificuldade de Manutenção: A classe Venda assume responsabilidades que não são dela (cálculo de regras de negócio complexas), tornando-se uma "Classe Deus".

Baixa Reutilização: Você não consegue isolar um cálculo de desconto para testá-lo individualmente (testes unitários) sem instanciar toda a lógica da venda.
